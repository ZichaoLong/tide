## 2. 为什么选 Qwen3-0.6B-Base

相比先前考虑的 `Qwen2.5-0.5B-Base`，`Qwen3-0.6B-Base` 更新，仍然是结构清楚的 text-only dense decoder，并且本机已经有经过文件校验的权重，也已有单芯 Ascend BF16 全参数 AdamW 成功运行记录。这能减少首轮环境与模型适配风险。

更近期的 `Qwen3.5-0.8B-Base` 于 2026 年发布，但它是带视觉编码器、Gated DeltaNet、周期性 full attention 和 MTP 的混合模型。它本身已经含有复杂循环状态，会让“新增 receiver 私有状态是否有效”更难归因。因此本日不选它；若 v0 在 Qwen3 上成立，再把它作为后续迁移对象。

真实运行必须把实际 checkpoint 文件哈希写进 manifest，不能只记录可变的模型名称。

## 3. 一个插入点怎样工作

设原 Qwen3 block 对当前 Token hidden 的输出为 $b_t\in\mathbb R^{1024}$。原 block 完整保留，它也是 always-on backbone。新增局部分支接在 block 之后：

```text
input hidden
    -> 原 Qwen3 block（始终执行） -> b_t --------------------------+
                                  |                                |
                                  +-> 固定 R0 / R1 / R2 / R3       |
                                      Observe / Update             |
                                      Top-1 receiver 执行 FFN       |
                                      其余 receiver 只保留状态      |
                                                   -> fixed add ----+-> output hidden
```

这里：

- **receiver** 是固定子节点槽位。每个 receiver 拥有 Observe 投影、128 维私有状态和自己的 FFN 参数。
- **Receive / Observe / Update** 是收到当前消息并更新小状态，四个 receiver 的邻接关系不随 Token 改变。
- **ExpensiveCompute** 是 receiver 内与原模型 MLP 同宽的 SwiGLU FFN。只有 Top-1 receiver 执行。
- **Emit** 是被激活 receiver 把 FFN residual 送到固定 merge；未激活 receiver 不产生 residual，也不继续传播。
- v0 只有一跳，所以 fixed merge 后立即回到共同 hidden；多跳留到后续实验。

## 4. 消息、选择和私有状态

### 4.1 当前消息与 Top-1 选择

先对 backbone 输出做 RMSNorm，得到当前公共消息：

$$
m_t=\operatorname{RMSNorm}(b_t).
$$

共享 router 只读取 $m_t$，不读取过去的 receiver state：

$$
p_t=\operatorname{softmax}(W_r m_t),\qquad
a_t=\arg\max_{i\in\{0,1,2,3\}}p_{i,t}.
$$

$a_t$ 是本次唯一执行昂贵 FFN 的 receiver。训练时加入一个小的概率均衡项：

$$
L_{\text{balance}}
=\sum_{i=0}^{3}\left(\overline p_i-\frac14\right)^2,
\qquad
L=L_{\text{LM}}+0.01L_{\text{balance}},
$$

其中 $\overline p_i$ 是一个训练 batch 内有效 Token 的平均 router 概率。它只防止一开始全部挤到同一 receiver，不使用设备负载或 batch 同伴改变单序列路由语义。

### 4.2 “衰减累积”是什么意思

receiver $i$ 在位置 $t$ 的动态状态记作 $s_{i,t}\in\mathbb R^{128}$。它不是模型参数，而是属于当前序列的运行时记忆。receiver 收到消息时，先形成新的观察：

$$
o_{i,t}=\tanh(W^{\text{obs}}_i m_t+b^{\text{obs}}_i).
$$

再把旧状态和新观察做指数移动平均：

$$
s_{i,t}^{+}
=\lambda_i\odot s_{i,t-1}
+(1-\lambda_i)\odot o_{i,t}.
$$

$\lambda_i$ 是限制在 $(0,1)$ 的可训练 128 维向量，初始化为 $0.99$。直观上，每次更新先保留约 99% 的旧摘要，再写入约 1% 的新观察；训练可以为不同维度改变保留速度。这就是本设置中的“衰减累积”。

实现中令 $\lambda_i=\operatorname{sigmoid}(\rho_i)$，从而训练时也不会跑出 $(0,1)$。Observe、状态累积和状态投影使用 FP32，投影回 hidden 后再转为 backbone 的 BF16。

如果 receiver 本次没有收到消息，则：

$$
s_{i,t}^{+}=s_{i,t-1}.
$$

状态按 `序列 × 插入点 × receiver` 隔离：新序列开始时清零；同一序列跨 chunk continuation 时必须保存和恢复；不同 batch 样本之间不能共享。v0 的训练样本长度固定为 512，样本结束即清零，不跨 optimizer step 保存神经状态。

### 4.3 两种传播 profile 唯一改变什么

令 $r_{i,t}$ 表示 receiver 是否收到并执行 Update，$c_{i,t}$ 表示是否执行昂贵 FFN：

| Profile | $r_{i,t}$ | $c_{i,t}$ |
| --- | --- | --- |
| `selected-dispatch` | $\mathbf 1[i=a_t]$ | $\mathbf 1[i=a_t]$ |
| BO | 对 4 个 receiver 都为 1 | $\mathbf 1[i=a_t]$ |

因此两组每个插入点都只执行一个昂贵 FFN。区别只是：未激活 receiver 在 BO 中仍看到当前消息并更新状态，在 `selected-dispatch` 中什么也不写。

v0 属于“selector 忽略 post-Update state”的配置。伪代码为了让两种 profile 共用同一路由，先计算 $a_t$；因为 router 只读取 $m_t$，这与先完成 BO Update、再使用同一个 $a_t$ 在数值上等价。

### 4.4 被选中后怎样读取状态

被选 receiver 先把更新后的状态投影回 hidden 维度：

$$
z_{a_t,t}=m_t+W^{\text{state}}_{a_t}s^{+}_{a_t,t}.
$$

然后才执行它自己的 SwiGLU FFN：

$$
e_{a_t,t}
=W^{\text{down}}_{a_t}
\left(
\operatorname{SiLU}(W^{\text{gate}}_{a_t}z_{a_t,t})
\odot W^{\text{up}}_{a_t}z_{a_t,t}
\right).
$$

新增输出以 router 概率加权后固定加回 backbone：

$$
h^{\text{out}}_t=b_t+p_{a_t,t}e_{a_t,t}.
$$

每个 receiver 的 FFN 输入、输出维度与 Qwen3 hidden 相同，中间维度沿用原模型 MLP 的 3072。$W^{\text{down}}$ 初始化为零，所以初始时 $e_{a_t,t}=0$，扩展模型输出与原模型相同；第一步应先给 $W^{\text{down}}$ 梯度，内部参数在输出投影离开零点后获得主任务梯度。

这条链说明私有状态怎样产生价值：receiver 在过去未被激活时写入消息；以后它被 Top-1 选中，ExpensiveCompute 通过 $W^{\text{state}}s$ 读取这些过去写入，进而改变 residual、logits 和 loss。

## 5. Reference 伪代码

```text
for each insertion point after the original Qwen3 block:
    b = original_block(hidden)              # always-on backbone
    m = rms_norm(b)
    probability, active_id = router(m)      # content-only Top-1

    for receiver i in fixed receivers [0, 1, 2, 3]:
        receive = (profile == BO) or (i == active_id)
        if receive:
            receiver_state[i] = ema_update(receiver_state[i], m)

    i = active_id
    z = m + state_projection[i](receiver_state[i])
    delta = expensive_ffn[i](z)             # only one receiver computes
    hidden = b + probability[i] * delta      # fixed residual merge
```

优化实现可以使用 mask、pack/scatter 或 scan，但必须与这段逐 Token reference 在 logits、状态和 route artifact 上一致。

## 6. 数据与训练预算

- 数据集：`HuggingFaceFW/fineweb-edu` 的 `sample-10BT` 配置，固定 revision `87f09149ef4734204d70ed1d046ddc9ca3f2b8f9`。
- 使用 Qwen3 原 tokenizer；文档之间加入 EOS，再按 512 Token 连续打包。
- 按固定文件和行顺序取前 100 万 Token 作为 validation、随后 1000 万 Token 作为 train；生成后的 Token 文件另记内容哈希。
- 单芯 NPU，micro-batch 4，gradient accumulation 4，每个 optimizer step 处理 8192 Token。
- AdamW：$\beta=(0.9,0.95)$、weight decay 0.1、gradient clip 1.0。
- Backbone learning rate 为 $10^{-5}$；新增 receiver、state、router 和 FFN 为 $10^{-4}$；前 5% steps 线性 warmup，之后 cosine decay 到初始值的 10%。
- 首轮每个训练组使用同一个 seed，各训练 1000 万 Token。只有出现正面信号后，才对 BO 与 matched `selected-dispatch` 补到 3 个 seeds。

上述 batch 是起始设置。若实际新增参数导致 OOM，只降低 micro-batch 并等量增加 gradient accumulation，保持每步 8192 Token 不变，同时在新的每日记录中说明。

## 7. 三个训练组与便宜诊断

| 组 | 设置 | 回答的问题 |
| --- | --- | --- |
| D0 | 原 Qwen3 continued pretraining | 不增加结构时，继续训练本身能改善多少 |
| S1 | 4 receivers、Top-1、`selected-dispatch` | 只有选中节点拥有历史时的 matched control |
| B1 | 与 S1 完全相同，仅切换为 BO | 未激活期间的状态写入是否有额外价值 |

D0 与另外两组的参数和 active FLOPs 不匹配，只是原 checkpoint 基线。首要因果比较是 S1 与 B1；两者必须具有相同参数、昂贵激活预算、初始化、训练 Token 和优化器设置。

B1 训练完成后直接做三种无需重训的验证干预：

1. `no-read`：保留状态更新，但把 $W^{\text{state}}s$ 置零。
2. `clear`：在指定位置清空 receiver state。
3. `shuffle`：在同一个 batch 内打乱不同序列的 receiver state。

如果这些干预不改变 logits 或 loss，就不能声称 BO 的延迟状态被实际使用。另做一个很小的 delayed-write/read 合成任务作为机制冒烟测试，但不把它当作自然语言 learning value。

## 8. 本轮输出和停止条件

每组至少输出：validation loss / perplexity、receive/update/active/read 次数、每个 receiver 的梯度覆盖、router 占用、状态范数与写入到读取间隔、训练吞吐和峰值显存。

按下面顺序决定是否继续：

1. checkpoint equality、save/reload 和任意 chunk continuation 先通过；
2. 零初始化分支能够离开零点并获得梯度；
3. B1 的状态干预可重复改变输出或 loss；
4. B1 相对 S1 出现 validation learning signal；
5. 前四项成立后，才进入多 seed、两层有界度扩展、flat MoE 和系统优化。

## 10. v1：平铺宽度筛选与标准 MoE 锚点

### 10.1 这轮只回答两个问题

1. 把固定 receiver 数从 4 增加到 8、16 后，SD 与 BO 是否仍能稳定训练，BO 是否仍与 matched SD 持平。
2. 在相同模型、数据和 Top-1 稀疏路由条件下，一个更接近成熟学界做法的无状态 MoE 能否稳定训练。它是训练可信度锚点，不是 TIDE 的替代结构。

暂不进入二层递归，也不做随机初始化的从头预训练。

### 10.2 五个训练组

| 组 | 结构 | 私有状态 | 每处每 Token 的昂贵 FFN 数 |
| --- | --- | --- | ---: |
| M8 | 将原 MLP 复制为 8 个 Top-1 专家；无容量上限，不丢 Token | 无 | 1 |
| S8 | always-on backbone 后接 8 个固定 receivers；只有 Top-1 Observe / Update / FFN | 8 × 128 维 | 1 |
| B8 | 与 S8 相同，但 8 个 receivers 都 Observe / Update，只有 Top-1 FFN | 8 × 128 维 | 1 |
| S16 | S8 的 receiver 数改为 16 | 16 × 128 维 | 1 |
| B16 | B8 的 receiver 数改为 16 | 16 × 128 维 | 1 |

M8 在 block `6, 13, 20, 27` 内替换原 MLP；S/B 仍在这些完整 block 之后增加 residual branch。因此 M8 用来回答“标准 Top-1 稀疏专家能否在本设置下工作”，不能与 S/B 做严格的参数量或 active FLOPs 因果比较。

M8 的伪代码是：

```text
experts = 8 copies of the original MLP
route = argmax(softmax(router(hidden)))
output = experts[route](hidden)       # Top-1 权重归一化为 1
```

所有专家初始权重完全相同，所以无论 router 选中谁，初始输出都等价于原 dense MLP。每个 Token 都进入一个专家，不设置 capacity，也不丢弃溢出 Token。router 使用两个常见约束：

$$
L_{\text{balance}}=N\sum_{i=1}^{N}f_i\bar p_i,
\qquad
L_z=\frac1T\sum_t\operatorname{logsumexp}(r_t)^2,
$$

其中 $f_i$ 是实际路由到专家 $i$ 的 Token 比例，$\bar p_i$ 是平均 router 概率，$N=8$。总损失为

$$
L=L_{\text{LM}}+0.01L_{\text{balance}}+0.001L_z.
$$

S/B 继续使用第 4 节的 EMA 私有状态和概率均衡项，只把 receiver 数 $N$ 从 4 改为 8 或 16；B 组的所有 receiver 更新状态，S 组只有 Top-1 更新状态。

### 10.3 共同训练设置

除结构宽度外，五组都沿用 v0：Qwen3-0.6B-Base、同一份 FineWeb-Edu 10M train / 1M validation Token、序列长 512、BF16、seed 42、block `6,13,20,27`、micro-batch 4、gradient accumulation 4、每步 8,192 Token、AdamW 与同一学习率日程。每组仍为 1,221 steps / 10,002,432 Token。

专家副本沿用 backbone learning rate `1e-5`；新 router 使用 `1e-4`。S/B 的所有新增参数继续使用 `1e-4`。短筛选每 500 steps 保存一次 checkpoint，并在结束时保存最终 checkpoint。

若 16 receivers 实测 OOM，唯一允许的机械调整是把 micro-batch 从 4 降为 2，同时把 gradient accumulation 从 4 增为 8，保持每步 Token 数不变；一旦发生必须在本节追加实测记录。

### 10.4 判定与下一阶段

- 稳定性硬门槛：跑满预算，无 NaN、OOM、梯度缺失或长期路由塌缩。
- 配对判断：分别比较 S8/B8、S16/B16；BO 能稳定且与 SD 持平即可，不要求 BO 更优。
- M8 判断：初始 validation 应接近 D0，并在 10M Token 内稳定下降；同时观察实际专家占用，确认没有只使用少数专家。
- 100M 阶段：只选择通过本轮的 `D / M / S / B`，从同一个原始 checkpoint 重新开始，在同一份 100M 不重复训练 Token 上比较；validation 仍固定为 1M Token。当前不循环现有 10M 数据，也不启动该阶段。
- 300M 阶段：只扩展 100M 后仍有希望的少数组合。

| 组 | 初始 validation loss | 最终 loss | 最终 PPL |
| --- | ---: | ---: | ---: |
| M8 | 2.783263 | 2.767244 | 15.9147 |
| S8 | 2.783254 | 2.764509 | 15.8713 |
| B8 | 2.783254 | 2.764460 | 15.8705 |
| S16 | 2.783254 | 2.764613 | 15.8729 |
| B16 | 2.783254 | 2.764561 | 15.8721 |

B8 与 S8 相差 `0.000050`，B16 与 S16 相差 `0.000051`，都应解释为持平。增加到 16 个固定 receivers 后，BO 仍能稳定训练；M8 也通过了“成熟 Top-1 稀疏路由在当前代码、数据和设备上能够训练”的锚点门禁。这些结果支持进入更长训练，但 10M Token 的 checkpoint 续训不能回答从随机初始化开始是否稳定。

## 11. P0：随机初始化的 1B Token 预训练

### 11.1 这一轮要回答什么

这一轮不再加载 Qwen3 的已有权重，而是从随机参数开始训练。目的不是在 1B Token 内得到实用模型，而是让下面三类问题真正有机会暴露出来：

1. Token 在训练中逐渐选择不同路径时，路径分布是否剧烈漂移或塌缩；
2. 越靠前的路由、状态与专家，能否持续得到来自最终语言模型 loss 的梯度；
3. BO 让所有 receiver 持续写入私有状态后，是否仍能像 matched SD 一样稳定训练。

BO 不需要优于 SD。若 B8 与 S8、B16 与 S16 的 loss 同量级，并且 BO 能跑满预算、路径和梯度没有失控，就达到了本轮目的。

### 11.2 六个独立训练组

| 组 | 结构 |
| --- | --- |
| P-D | 原始 dense Qwen3 结构 |
| P-M8 | 在 block `6,13,20,27` 内使用 8 专家 Top-1 MoE |
| P-S8 | 4 个 block 后各接 8 receivers；只有 Top-1 Observe / Update / FFN |
| P-B8 | 与 P-S8 参数完全相同；8 个 receivers 都 Observe / Update，只有 Top-1 FFN |
| P-S16 | P-S8 的 receiver 数改为 16 |
| P-B16 | P-B8 的 receiver 数改为 16 |

六组各自是独立任务，会分别等待任意一张满足条件的空闲 NPU，不在一个串行脚本里互相等待。P-S8/P-B8 使用同一个 seed 和相同的初始化顺序，因此初始参数逐项相同；P-S16/P-B16 也相同。两组 matched pair 唯一的语义差别仍是未选 receiver 是否 Observe / Update。

### 11.3 模型从哪里开始

- 复用 `Qwen3-0.6B-Base` 的 config 和 tokenizer：28 层、hidden 1024、MLP intermediate 3072、词表 151,936。
- 不读取 checkpoint 权重；manifest 会明确记录 `config and tokenizer only`，也不会把权重文件哈希误写成初始化来源。
- 所有组使用 seed 42 和 BF16；router、Observe 与 128 维私有状态仍使用 FP32。
- P-M8 在每个插入层先随机初始化一个普通 MLP，再把它逐项复制成 8 个专家，因此初始时无论选哪个专家都等价于该层原 MLP。
- P-S/P-B 的新增 FFN 输出投影仍从零开始，所以初始 residual 分支为零；它会先离开零点，再逐渐让内部 Observe、state projection 和 FFN 获得主任务梯度。

因此六组在初始化时都应与同 seed 的 P-D 给出相同或数值容差内相同的 validation loss；若这一门禁不成立，不开始解释后续结构差异。

### 11.4 数据、batch 和更新次数

- 数据仍是 FineWeb-Edu `sample-10BT`，revision 固定为 `87f09149ef4734204d70ed1d046ddc9ca3f2b8f9`，文档之间加入 EOS。
- validation 文件保存 1,000,000 Token；每次评估读取其中 1,953 个完整序列，即 999,936 Token。
- train 文件保存 1,000,013,824 Token。它恰好覆盖全部 15,259 个 optimizer steps，不循环、不重复使用开头样本。
- 序列长 512，micro-batch 4，gradient accumulation 32，所以每次 optimizer update 处理

$$
4\times32\times512=65{,}536\ \text{Token}.
$$

计划里程碑按“处理 Token 数第一次达到目标”触发：

| 目标 | optimizer step | 实际已处理 Token |
| ---: | ---: | ---: |
| 10M | 153 | 10,027,008 |
| 100M | 1,526 | 100,007,936 |
| 300M | 4,578 | 300,023,808 |
| 1B | 15,259 | 1,000,013,824 |

每个里程碑都保存 checkpoint、跑固定 validation，并执行下一节的 probe。这样同一个 1B 训练任务自然包含 10M、100M、300M 和 1B 四个观察点，不需要把数据阶段拆成四次重新训练。

checkpoint 保存模型、AdamW、数据游标和随机数状态，因此可以完整续训，但单个文件约为 3.9--7.7GB。每个 run 只保留最新的 1 个完整 checkpoint：新文件完整写入且 `latest.json` 原子切换后，才删除更旧文件。各里程碑的 validation、probe、原始 metrics 和删除审计继续保留，所以长期曲线与诊断不会随 checkpoint 清理丢失。

### 11.5 优化器和学习率

所有随机初始化参数使用同一个学习率，不再区分 backbone 与 extension：

- AdamW，$\beta=(0.9,0.95)$，weight decay 0.1；
- gradient clip 1.0；
- 基础学习率 $3\times10^{-4}$；
- 前 20M Token 线性 warmup，之后保持不变：

$$
\operatorname{lr}(n)
=3\times10^{-4}\min\left(1,\frac{n}{20{,}000{,}000}\right),
$$

其中 $n$ 是已经用于训练的 Token 数。使用 Token 而不是“总步数百分比”定义 warmup，是为了以后从 1B 直接续到更长预算时，不必改写已经走过的学习率轨迹。

P-S/P-B 继续使用 `0.01 × probability balance loss`；P-M8 使用 `0.01 × Switch-style balance loss + 0.001 × router z-loss`。其它损失定义与第 4、10 节相同。

### 11.6 固定 probe 怎样看路径、信用和状态

probe 固定读取 validation 开头 65,536 Token，并在初始化、10M、100M、300M、1B 五个时点执行。它不改变训练数据或参数。

对每个 Token $x_t$，把四个插入层的 Top-1 选择依次写成完整路径：

$$
\pi(x_t)=(a_{6,t},a_{13,t},a_{20,t},a_{27,t}).
$$

记录项保持在三个粗粒度上：

- **路径漂移**：每层 receiver 占比与熵、有效 receiver 数、完整路径熵与有效路径数，以及相对初始化时有多少 Token 改变了完整路径；
- **分层信用**：每个插入层分别记录 router、Observe、state projection 和昂贵 FFN 输出投影的梯度范数与梯度覆盖；M8 对应记录 router 和专家输出投影；
- **状态因果干预**：正常 probe 之外再做 `no-read`、序列中点 `clear`、序列中点跨 batch 样本 `shuffle`，记录相对正常 probe 的 $\Delta\text{loss}$。

`no-read` 保留状态更新但不把状态投影给 FFN；`clear` 在第 256 个位置前把状态清零；`shuffle` 在同一位置把不同样本的状态互换。若三者始终都不改变 loss，说明私有状态虽然在更新，却没有对预测产生可测影响。它是解释性诊断，不要求 BO 必须因此优于 SD。

### 11.7 记录、停止条件和当前状态

每组的 `manifest.json`、原始 `metrics.jsonl`、最新完整 checkpoint、checkpoint 删除审计、probe artifact 和 `result.json` 是权威记录；Trackio 项目 `tide-p0-pretrain` 只同步标量，使用 best-effort 模式，服务异常不能中断训练。

硬停止条件只有非有限 loss、OOM、运行时错误或记录/checkpoint 失败。路由偏斜、BO 不优于 SD、状态干预很小都先作为实验结果保留，不在中途主观停止。最终主要看六组能否跑满、matched pair 是否同量级，以及路径与分层梯度随 Token 的变化。

正式任务使用 commit `10500b0034f013ae45be14c25c969903e840c7b1` 的冻结源码快照。1-step P-B8 NPU 门禁已完成，六个独立 user-systemd unit 都已提交给本账户的自动空闲卡队列；检查时 P-D、P-S8、P-B8 分别在一张映射为 `npu:0` 的 NPU 上运行，P-M8、P-S16、P-B16 仍各自排队，不存在组间串行依赖。

截至本地时间 2026-08-21 20:55，P-D 已到 107.5M Token，100M validation loss 为 `4.129782`；P-S8、P-B8 分别到约 53.7M、53.1M Token，10M validation loss 为 `6.861246`、`6.875258`。三组尚未出现非有限 loss、OOM 或任务失败；这些是中途状态，不是最终比较结论。

### 11.8 checkpoint 空间策略

本机运行根目录使用十进制 100GB 上限。2026-08-21 的首次整理删除了 v0/v1 中间 checkpoint、已被 `latest.json` 替代的 P0 checkpoint 和已完成 disposable smoke 的模型/优化器张量，共释放约 140.6GB；所有配置、metrics、validation、probe、结果与逐文件审计均保留。整理后占用为 65.68GB。

当前 P0 使用冻结源码，所以由独立 unit `tide-p0-checkpoint-retention-r1` 每 30 秒检查一次，每个训练组只保留 `latest.json` 指向的完整 checkpoint。后续源码中的 `--checkpoint-keep-last` 默认值为 1；显式设为更大的数才保留更多版本，设为 0 才关闭单 run 自动清理。本机总量上限属于运行环境策略，不写入模型或跨平台训练代码；新任务启动前仍需把已有保留量和一次原子写入所需的临时空间计入预算。
