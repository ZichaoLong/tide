# 2026-08-22 实验记录

本文记录 P0 随机初始化预训练的 300M 结果，以及八层深路径压力测试启动前的门禁修复。这里的 Token 都指已经用于训练的 Token 数；validation 使用固定的 1M Token，probe 使用 validation 开头固定的 65,536 Token。

## 1. 四层基线到 300M 的结果

所有任务继续使用随机初始化的 Qwen3-0.6B 结构、FineWeb-Edu `sample-10BT` 数据、序列长度 512、BF16、seed 42、AdamW 和 20M Token 线性 warmup。D0 是普通 dense backbone；M8 是 8 专家的标准稀疏 MoE 对照；S8/B8 分别是每处 8 receivers 的 selected-dispatch 和 broadcast-observe；S16/B16 把 receiver 数增加到 16。S/B 都在 block `6,13,20,27` 插入四处路由模块。

六组均没有 failure、非有限 loss、OOM 或梯度链断裂。S8/B8 的 300M validation loss 相差不到 `0.0005`，因此 BO 到四层、300M 时仍能与 SD 稳定持平。

S8/B8 相对初始化改变完整路径的 Token 比例分别为 `99.9786%` 和 `99.9603%`；有效完整路径数从 10M 的 `161.39/175.12` 回升到 300M 的 `579.63/528.62`。这说明路径分配发生了很强的重组，但暂时没有演变成训练失败。两组四个插入层的 router、Observe、state 和 FFN 梯度都非零，8 个 receiver 均有路由。300M `no-read` 干预的 $\Delta\text{loss}$ 分别为 `0.00552/0.02818`，BO 的私有状态已经产生更明显的可测影响，但这仍只是单 seed 的固定 probe。

S16/B16 在 10M 已出现明显的 receiver 饥饿：各层有效 receiver 约为 5–9 个，层 27 各有一个 receiver 在固定 probe 中没有路由；其它梯度组仍非零，目前没有发现专家饥饿以外的新失败模式。

## 2. D8 NPU 门禁为何补跑

D8 正式组保持总 receiver FFN 数为 32，只把顺序路由深度从四处增加到八处：

- 插入 block：`3,6,10,13,17,20,24,27`；
- 每处 4 receivers；
- S4-D8 使用 selected-dispatch，B4-D8 使用 BO；
- 首阶段训练 300M Token，里程碑为 10M、100M、300M；
- 两组使用同一冻结源码 commit `7c6e4f7160ee166178617e758f99525391946183`，分别独立排队，优先级为 10。

第一次全尺寸 B4-D8 NPU smoke 完成了 1 个训练 step、validation 和 checkpoint，peak HBM 为 11.83GB；8 个插入层的 router/FFN 梯度非零，Observe/state 梯度张量存在但第一步范数为零。它证明了全尺寸图可以在 NPU 上前后向和保存 checkpoint，但 manifest 的 `repository.commit` 被记录成 `null`，所以自动提交器拒绝了它。

原因不是源码内容错误：外层 launcher 已验证冻结 worktree 的 commit，但 workload 没有先进入该 worktree；manifest 又从当前工作目录读取 Git 身份。修复后的 `smoke-b4d8-r2` 不覆盖第一次记录，并做两项加强：

1. 运行前显式进入冻结源码 worktree，使 manifest 自己记录并验证 commit；
2. 执行 2 个 optimizer step，要求第二步八个插入层的 router、Observe、state、FFN 梯度范数全部有限且大于零。

smoke r2 以独立 unit `tide-p0-deep-smoke-b4d8-r2.service`、优先级 20 提交；`tide-p0-deep-gate-submit-r2.service` 会在它和既有 100M 门禁都通过后，分别提交 S4-D8/B4-D8。检查时 16 张 NPU 都有进程，smoke r2 是队首等待者，尚未分配设备。

## 3. checkpoint 上限修复

运行根目录继续使用十进制 100GB 的稳定占用上限。旧保留监控在训练原子保存 checkpoint 时遇到竞态：`du` 正在遍历的临时文件被原子重命名，返回码 1 被当成致命错误，导致监控退出。

修复后，稳定占用统计忽略 `.*.tmp-*` 原子临时文件，并对“文件瞬时消失”最多重试 5 次；只有这种明确的竞态可以降级接受最后一次统计，权限错误或其它 `du` 异常仍会失败。新 unit 为 `tide-p0-checkpoint-retention-r2.service`。

清理前逐组核对 `latest.json`：D0/S8/B8 都已指向 300M checkpoint。随后删除三者被替代的 100M checkpoint，共释放 `15.49GB`，每个删除事件均写入 `checkpoint-retention-20260821-r1/events.jsonl`。清理后的稳定占用约为 `75.32GB`；smoke 与正式 D8 任务后续仍各自只保留最新一个完整 checkpoint。

监控重启后，M8 的 `latest.json` 从 10M 原子推进到 100M；修复后的 watcher 正常删除了被替代的 10M checkpoint，没有再次因并发保存退出。第一次 D8 smoke 的 metrics、manifest、result 和失败原因已经保留，其 disposable checkpoint 也完成审计删除，进一步释放 `5.80GB`；此后运行根目录稳定占用约为 `69.52GB`。
